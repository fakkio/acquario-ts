# v0.1 stack: Canvas2D, OOP, main thread, no persistence, hard walls

A pure client-side browser application with no backend. Rendering is Canvas2D; simulation data is OOP classes rather than SoA typed arrays; the simulation runs on the main thread with a fixed-step accumulator decoupled from `requestAnimationFrame`; there is no persistence; the world is finite and bounded by hard walls. Toolchain: npm, Vite, Vitest, TypeScript strict, ESLint + Prettier.

## Why

Each choice trades a known future cost for present simplicity, with the WebGPU migration kept in mind but not allowed to complicate v0.1:

- **OOP over SoA** — simpler to write now, at the cost of a larger rewrite of hot-path data when WebGPU requires flat buffers.
- **Main thread over a Web Worker** — class instances are not structured-cloneable, so a worker would mean serialising state every tick merely to stay in sync. To be revisited only if profiling shows a real bottleneck, at which point OOP would be revisited too.
- **No persistence** — adding it now would mean versioning a genome schema that is still moving. Revisit once the formats settle. (CSV export of run statistics is not persistence; see ADR-0011.)
- **Hard walls over toroidal wraparound** — a fixed-size collision grid is simpler, and the aquarium metaphor needs a real surface and floor for the light gradient to be meaningful.

## Consequences

- World quantities are expressed as rates over time and multiplied by `dt`, never per frame. If rendering falls behind, the accumulator runs multiple fixed ticks with a catch-up cap, so a pathologically long frame cannot trigger a recovery storm.
- No population target is set for v0.1: build, profile, and let the stack find its natural limit. Needing to exceed it is the trigger for reconsidering WebGPU.
- TDD applies to pure deterministic logic — metabolism, genome and mutation, grid queries, the neuron update rule — but not to rendering or the animation loop, which are verified by running the app.
